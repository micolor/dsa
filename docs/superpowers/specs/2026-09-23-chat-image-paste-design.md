# 问股支持贴图 — 设计文档

> 目标：让 Web 问股（`/chat`）的输入框能**粘贴/拖入一张图**，AI 既回答关于这张图的问题，
> 也能从中提取股票代码；用户明确要求时，通过已有的确认卡片把代码加进自选。
>
> 方案是**视觉前置 + 文本注入**：图片在进入对话前先被视觉模型看一遍，结果作为文本注入当轮消息；
> agent 主模型、工具循环、`llm_adapter`、`executor`、runner **一行不改**。图片二进制**不落盘**。

## 1. 背景与现状

### 1.1 聊天现在完全不支持图片

| 层 | 位置 | 现状 |
| --- | --- | --- |
| 接口 | `api/v1/endpoints/agent.py:56-71` | `ChatRequest.message` 是裸 `str`，无任何图片/附件字段；三个 chat 端点全是 JSON |
| agent 链路 | `src/agent/executor.py:749-753` | 消息全程按纯字符串构造，仓库内没有任何地方构造 `{"type":"image_url"}` 内容块 |
| 前端 | `apps/dsa-web/src/pages/ChatPage.tsx:1844-1879` | composer 是纯 `<textarea>`；无 file input、无粘贴/拖放处理、无附件状态 |
| bot | `bot/platforms/feishu_stream.py:450-454` | **显式丢弃非文本消息**（本次不做 bot，见 §2） |

### 1.2 仓库里已有的图像能力，以及它在当前配置下**静默失效**

设置页有一个独立功能：`POST /api/v1/stocks/extract-from-image`（`api/v1/endpoints/stocks.py:113-176`，
multipart）→ `src/services/image_stock_extractor.py` 的截图提取股票代码。它**不接触聊天**。

2026-09-23 实测（本机配置）证明它**什么都没做，却返回 200**：

| 输入 | 结果 |
| --- | --- |
| 1×1 空白 PNG | `codes: []`，`raw_text: "[]"`，1.05s |
| 600×220、90px 清晰写着 `600519` / `Guizhou Moutai` 的 PNG | `codes: []`，`raw_text: "[]"`，**1.19s** |

两张内容天差地别的图给出**完全相同**的输出与耗时 → 图片没有被看到，模型只读了文字提示。

**根因（逐层实测定位）**：

1. 本机唯一配置的 LLM 渠道是 DeepSeek（`deepseek-v4-flash` / `deepseek-v4-pro`，`api_base=https://api.deepseek.com`），`VISION_MODEL` 为空，`_resolve_vision_model()` 兜底到 `litellm_model`。
2. **`deepseek-v4-flash` 本身支持视觉**：绕过 litellm 直发原始 HTTP（`POST /chat/completions` + `image_url` 内容块）能正确读出 `600519` / `Guizhou Mout`。
3. **litellm 的 `deepseek/` provider 路由会剥掉图片部分**：同一张图经 `litellm.completion(model="deepseek/deepseek-v4-flash", …)` 回去时模型明确回答「未收到图片」（多模态载荷下还出现过 403）。给该模型 `litellm.register_model({…"supports_vision": True…})` **不能**修复 —— 是 provider 适配器的问题，不是能力元数据。
4. **可行修法（已验证）**：改用 litellm 的通用 OpenAI 兼容路由 **`openai/deepseek-v4-flash` + 同一个 `api_base`**，图片正常通过、模型读出内容。

**为什么这个缺陷能发货**：接口返回 200 + 空列表，看起来像「这张图里没有股票代码」；而它的测试在
`tests/test_image_stock_extractor_litellm.py:171` **patch 掉了 `litellm.completion`**，按构造抓不到
「图没被转发」。本次设计把这条作为必须堵死的一类问题（§8 不变式、§10 的"真转发测试"）。

### 1.3 可复用的既有资产

- 视觉调用配方：`image_stock_extractor._call_litellm_vision`（`:309-381`），内容块构造在 `:346-360`
- 视觉模型解析：`_resolve_vision_model()`（`:250-266`）
- 图片输入校验：MIME 白名单 + 5MB 上限（`:80-81`）、magic-byte 校验（`:93-106`）
- 前端拖放与文件选择交互范式：`apps/dsa-web/src/components/settings/IntelligentImport.tsx:203-209`（拖放）、`:320-326`（`accept=".jpg,.jpeg,.png,.webp,.gif"` 的隐藏 input）
- 确认卡片与提案通道（刚交付）：`propose_watchlist_change` → `action_proposal` → 卡片 → 用户确认后浏览器调 `POST /api/v1/stocks/watchlist/add`

## 2. 目标与非目标

**目标**

1. Web 问股输入框支持**粘贴**（主）、**拖放**、**文件选择**三种入口贴一张图。
2. AI 能**回答关于这张图的问题**（截图作为问题上下文）。
3. AI 能**从图中提取股票代码**并列出；用户明确要求时，通过既有确认卡片把代码加进自选。
4. 图片二进制**不落盘**；历史里只留文本结果，因此后续轮次 AI 仍"记得"它看到了什么。
5. 顺带修好 §1.2 的静默失效：视觉调用路由 + 无视觉模型时明确报错 + 真转发测试。

**非目标**

- **不做 bot / 飞书图片**：bot 现在直接丢弃非文本消息，要支持得另加图片消息类型处理与从飞书下载图片，且 `BotResponse` 是纯文本一次性回复（无流式、无卡片），交互形态与 Web 完全不同。另起一次设计。
- **不做多图**：第一版每轮最多 1 张。
- **不做图片持久化与回看**：刷新即失；不新增附件表/目录。这是本设计接受的代价——AI 靠文本摘要回答后续追问，而不是原图。
  **该承诺覆盖日志**：上游异常文本可能包含 `api_base`、模型名，某些 provider 还会回显请求体（**含 base64 图片本身**），
  所以诊断日志必须**脱敏后再写**（异常类型 + 裁剪并抹掉疑似 base64 长串的文本），不得把上游返回的原始文本整段落盘。
- **不做"图里代码一键触发分析"**：只做加自选（用户下一句说要分析即可）。
- **不改 `EXTRACT_PROMPT`**（`src/services/image_stock_extractor.py:37-55`）：`AGENTS.md` 规定改它必须在 PR 描述里附完整最新 prompt，说明它是被当作调优资产对待的；设置页那条提取路径继续用它。
- **不改共用 agent 路径**：`llm_adapter` 的消息转换、`executor` 的消息构造、runner 的工具循环都不动。
- **不新增配置项**：复用已有的 `VISION_MODEL`；路由修复不需要新配置。

## 3. 数据流

```
用户在 composer 贴图（+ 可能一句话）
        │  base64 + mime 随 POST /api/v1/agent/chat/stream 一起提交
        ▼
ChatRequest 校验（MIME 白名单 / 2MB 上限 / magic byte）
        ▼
【视觉前置】调一次视觉模型（走修好的 openai/ 兼容路由）
   prompt = 用户的问题（若有）+ 要求输出：与问题相关的图像内容 + 图中股票代码/名称(JSON)
        ▼
解析结果 → 拼成一段文本块 → 注入当轮用户消息
        ▼
既有的 agent 路径（文本模型 + 工具循环，一行不改）
        ▼
回答里含代码；若用户表达了加自选意图 → 模型调 propose_watchlist_change → 确认卡片
        ▼
注入后的文本进 conversation_messages（后续轮次可见；原图不可见，见 §2 非目标）
```

## 4. 视觉调用路由修复（前置，必须先做）

`_call_litellm_vision`（`src/services/image_stock_extractor.py:309-381`）当前把
`_resolve_vision_model()` 的结果直接当 `model=` 传给 litellm。对 OpenAI 兼容 provider 必须改用
**`openai/<model>` 前缀**（`api_base` 已是 deployment 的参数，无需改），否则图片被剥掉。

- 该函数已有 `gemini/` / `anthropic/` / `vertex_ai/` 的前缀分支（`:368-372`），按同类方式加一支
  处理"OpenAI 兼容 provider"：模型名不带这些已知前缀时，用 `openai/` 前缀路由。
- **判断依据放在一处**：新增一个小函数（如 `_vision_wire_model(model, deployment_params)`）承担这个
  映射，避免调用点各自判断。
- **无可用视觉模型时明确报错**（现在 `_resolve_vision_model()` 返回空时会报，但兜底到文本模型后
  就变成了静默 `[]`）：当解析出的模型/路由不具备视觉能力时应抛明确错误，让上层能告诉用户。
- `EXTRACT_PROMPT` 及其解析、重试、去重逻辑**不动**；设置页那条路径因此顺带被修好。

## 5. 接口契约

`api/v1/endpoints/agent.py` 的 `ChatRequest`（`:56-71`）新增两个可选字段：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `image_base64` | `Optional[str]` | 与 `image_mime` 同时出现或同时缺省；解码后 ≤ **2MB** |
| `image_mime` | `Optional[str]` | 必须在 MIME 白名单内（复用 `image_stock_extractor` 的白名单） |

- **2MB 而非提取器的 5MB**：聊天请求体是 JSON、base64 会放大 ~1.33 倍，且还要带上会话上下文。
  超限返回 **400** 且 message 明确（"图片过大，上限 2MB"），不是静默忽略。
- magic-byte 校验复用 `_verify_image_magic_bytes`（`:93-106`）。
- **只加字段，不改既有字段语义**；三个 chat 端点中，`/chat/stream` 与 `/chat` 都接受图片（`/chat/send`
  是转发到通知渠道的接口，与图片无关，不加）。
- 前端 `ChatStreamRequest`（`apps/dsa-web/src/api/agent.ts:23-27`）同步加这两个字段。

## 6. 注入文本的形态

视觉结果拼成一段**明确的、带边界的文本块**注入当轮用户消息，形如：

```
【图片内容】<与用户问题相关的图像描述>
【图中股票】600519 贵州茅台；000858 五粮液
【用户问题】<用户原话（若有）>
```

- 三块都可能缺省（无代码时省略第二块；无文字问题时省略第三块）。
- 注入发生在进入 agent **之前**，因此模型看到的就是一条普通文本用户消息——**这是本方案不改共用
  路径的根本原因**。
- 注入后的完整文本进 `conversation_messages`，后续轮次自然可见。
- **只要请求里带图就必然触发视觉前置**，不因用户的文字看起来与图无关而跳过（跳过就会退化成
  §8 那个"看起来成功但图没被看到"的失败模式）。
- 有图无文字时（用户只贴图不说话）：视觉 prompt 按"总结这张图中与股票分析相关的信息并列出代码"处理。

## 7. 提示词规则（触发条件刻意写窄）

两套 chat 提示词（`LEGACY_DEFAULT_CHAT_SYSTEM_PROMPT`、`CHAT_SYSTEM_PROMPT`）各加一条，置于规则 9 之后：

```
10. **图中股票的加自选提案** — 当用户提供了图片、且消息里已列出图中股票代码时：**只有**当用户明确
表达了「把图里这些加入自选/自选股/关注」的意图，才用 `propose_watchlist_change` 逐个生成提案交由用户
确认；**仅因为图中出现代码不得主动提案**，此时只在回答中列出代码与名称即可。
```

**为什么触发条件要写这么窄**：上一个计划踩过"触发条件过宽 → 模型在没人要求时开卡片"的坑（当时的
「或对话中已确认份额与成本时」是对话状态条件，假设句与复盘闲聊都会误触发）。这里同样只认**明确意图**。

## 8. 失败与降级

| 情况 | 行为 |
| --- | --- |
| 无可用视觉模型 / 视觉调用失败 / 返回空内容 | **请求失败**：在校验阶段（`StreamingResponse` 之前）返回明确错误，**不**降级成"看不到图也照样回答"——那正是"看起来成功"的变体，且模型在不知道图内容时给出的回答毫无价值、还可能编造。状态码用 **503**（与本仓库既有的"所需依赖不可用"惯例一致，见 `history.py` / `screening_service.py`），**body 只放固定中文文案**，上游异常原文只进日志 |
| 图片超限 / 格式不支持 / magic byte 不符 | 前端先拦（即时反馈、不发送），后端再拦（400 + 具体 message） |
| 视觉结果里没有代码 | 正常回答，不提案 |
| 视觉结果里代码无法识别该市场 | 照原样列出，不猜不补 |

> **为什么 503 的 body 不能带上游异常原文**：前端的错误分类器（`apps/dsa-web/src/api/error.ts`）会**先**按字符串匹配 `timeout` 一类的关键词，再做别的判断；而视觉调用最常见的真实失败恰恰是超时。于是"图没被读到"会被显示成「请检查当前网络与代理设置」——把用户引向一个错误的方向。另外 litellm 的异常文本可能包含 `api_base`、模型名，某些 provider 还会回显请求体（**含 base64 图片本身**），而本仓库自己的 `api/middlewares/error_handler.py` 明确要求不要把内部细节外泄。

> **为什么不能靠运行期检查兜底**：2026-09-23 观测到的失败**不是空响应**——模型回了合法的 `"[]"`，
> 只是它是"看不见图"的情况下回答的。`_call_litellm_vision` 本来就会在响应为空时抛错，但对"瞎着
> 回答"完全无效。**所以这条不变式只能由 §10 那条真转发测试来守**，不能指望运行期判断。

**核心不变式（本设计的承重墙）**：**任何情况下都不得出现"看起来成功但图根本没被看到"。**
现网那个回 200 + 空列表的静默失效正是这个不变式的反例，必须有测试把它钉死（§10）。

## 9. 前端（`apps/dsa-web`）

### 9.1 注入块的渲染约定（**哨兵必须在注入时就存在，事后无法补**）

带图那一轮持久化的用户消息**就是**注入后的文本（`block + "\n" + 用户原话`）。而会话在**刷新或切换后**
是从库里还原的（`agentChatStore.ts` 把 `content` 原样映射，`ChatPage` 把用户气泡按原文本逐行渲染），
所以**注入块会以"用户自己说的话"呈现**——二进制按设计已丢，那段文字又与手打文本无法区分。

因此约定：**持久化的用户消息若以 `【图片内容】` 开头，即视为"含图片注入的轮次"**，前端据此把它折叠
成一行提示（如「[图片] 已由 AI 读取」+ 可展开原文），而不是把整段倒给用户当自己的话。

- 这条**不需要后端额外加标记**：`【图片内容】` 已经排在注入文本最前（`_render_block`），用它当哨兵即可。
- **但它必须在实现注入时就这样定下来**：库里那一行是 `request.message` 唯一存世副本，将来再加一个
  更显眼的标记无法追溯既有数据。所以本约定随注入一起固化。
- 连带要求：还原会话时的"活跃标的上文"解析（`restoreActiveStockContextFromMessages`）**只能看
  `【用户问题】` 之后的部分**，否则带图的轮次会因为块里列了 ≥2 个代码而让会话在刷新后静默进入
  "对比模式"——同一会话刷新前后行为不一致。


- **composer**（`ChatPage.tsx:1844-1879`）：三个入口——粘贴（`onPaste` 读 `clipboardData.files`，主路径）、拖放（复用 `IntelligentImport.tsx:203-209` 的范式）、隐藏 file input（`accept` 同 `:320-326`）。
- 选中后显示**待发送缩略图 chip**（可删除）；每轮最多 1 张，再贴一张则替换并提示。
- 发送时把 base64 + mime 放进既有请求体（`ChatPage.tsx:856-863` 那处构造）——**不新增端点、不做上传生命周期**。
- 用户消息在会话内用 blob URL 渲染原图；**刷新即失**（与"不存二进制"一致）。
- 超限/格式不符在**选中时**即时拦截并提示，不发请求。

## 10. 验证矩阵

- **后端单测**：
  - `ChatRequest` 校验：超限 → 400；未知 MIME → 400；magic byte 不符 → 400；字段成对出现
  - 注入文本形态：有代码 / 无代码 / 有文字问题 / 无文字问题 四种组合
  - 无可用视觉模型 → 明确错误且当轮仍有文字回答
  - 视觉调用失败 → 降级路径
  - **用户未表达加自选意图时不生成提案**（对应 §7 的窄触发条件）
- **真转发测试（承重墙）**：用一张**渲染了股票代码**的图，断言提取结果**包含该代码**。
  这条专治"mock 掉 `litellm.completion` 导致图没被转发也全绿"——诊断时已验证这张图的构造方式可行
  （PIL 渲染 `600519` + `Guizhou Moutai`）。**不得 mock 掉转发层**；若 CI 无网络，则该测试按仓库既有
  做法标记为 network 类并在交付说明里写明未在离线环境验证。
- **端到端（手工）**：起服务 → 界面粘贴一张图 → 回答里出现代码 → 说「把这几只加入自选」→ 出确认卡片
  （复用刚交付的通道）→ 确认 → 自选页出现 → **清理并核对自选恢复原状**（自选是用户数据）。
- **前端单测**：三条入口（粘贴/拖放/按钮）、缩略图与删除、超限即时拦截、消息内渲染、请求体含图片字段。
- 回归：`pytest -m "not network"` 的失败集与基线比对（**本仓库有约 88 条既有平台性失败，不能用失败数
  判断回归**——见 `docs/superpowers/plans/2026-09-22-…` 的做法：逐用例去基线重跑）。

## 12. 风险与回滚

**风险**

1. **视觉质量依赖 `deepseek-v4-flash` 的多模态能力，只在一台机器、一个 provider 上验证过**。图片大小、
   图表密度、截图清晰度都可能影响提取准确率。缓解：注入文本里同时给出原始代码与名称，让用户能看出
   提取错误；且加自选**必经确认卡片**，AI 提取错也不会直接写进用户的配置。
2. **2MB 上限可能挡住部分手机截图**。缓解：前端即时提示并给出明确文案；上限是常量，调整成本低。
3. **注入文本会占用上下文**：一张信息密集的截图，视觉模型可能输出几百字。缓解：prompt 里要求
   "只输出与问题相关的部分"且限制长度；上限可观测（注入文本进日志）。
4. **`openai/` 前缀路由对非 OpenAI 兼容 provider 是否安全**：修改按"已知前缀优先、其余走 openai 兼容"
   的次序做，且**只影响视觉调用这一个函数**，不碰 agent 主调用路径。
5. **不落盘带来的能力缺口**：用户刷新后无法回看原图，AI 也只能靠摘要回答追问。这是明确的设计取舍
   （§2 非目标），但要在 UI 文案与文档里说清，避免用户以为图被保存了。

**回滚**：整体 revert 单个 commit 序列即可。无数据库迁移、无新表、无新配置项；前端产物重启重建。
回滚后已产生的自选变更照常存在（那是正常业务数据）。

**已知的既有盲区（不在本计划范围，但值得单独立项）**：设置页那个"视觉能力检测"
（`src/services/system_config_service.py:1831-1882`）**对本次修的这类故障是瞎的**——
它发一张 **1×1 透明 PNG**，并且只要响应内容非空且可解析就报 `vision: passed`，从不检查
模型是否真的描述了图。于是在一条会剥图的路由上，它要么"报通过而其实是瞎的"（预修状态下
模型回的「未收到图片」就是非空内容），要么在 403 变体上不透明地失败。这是**既有问题**，
不是本计划引入的，但它恰恰是维护者排查"图没生效"时会先跑的工具。建议作为后续项：
让该探针复用本计划在 `image_stock_extractor` 里建立的同一份路由映射（设计 §4 的"判断依据
放在一处"），并改用一张**渲染了已知内容**的图 + 断言回复确实描述了该内容。
